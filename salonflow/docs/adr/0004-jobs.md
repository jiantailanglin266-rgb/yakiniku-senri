# ADR-0004: Phase 1 はインプロセスのジョブ実行にする

- 状態: 採用（Phase 3 で見直し）
- 日付: 2026-08-03

## 背景

仕様書 §3 は BullMQ または同等のジョブキューを推奨している。
BullMQ は Redis を必要とする。

## 決定

Phase 1 は Redis を要求せず、通知の配送を以下で行う。

- Outbox テーブル（`Notification` / `NotificationDelivery`）に永続化
- `POST /api/v1/jobs/notifications` を外部スケジューラが叩いて配送
- 配送は条件付き UPDATE で claim するため、多重起動しても二重送信しない

## 理由

- Phase 1 の完成条件に「README から環境構築できる」がある。
  Redis を必須にすると、PostgreSQL に加えてもう 1 つミドルウェアが要る。
- 通知の永続化と再送ロジックは Outbox 側にあり、キューの実装には依存しない。
  Redis を足すのは配送の駆動方法を変えるだけになる。
- 実行環境に Redis が存在しなかった。

## 帰結

### 良い点

- 依存が PostgreSQL のみ。
- 配送状態が DB にあるため、失敗の調査が SQL でできる。

### 悪い点（リスク R-16）

- **複数インスタンス構成では、条件付き claim があっても
  スケジューラの設定次第で重複起動しうる。**
- 遅延実行（リマインド通知）の精度がスケジューラの間隔に依存する。
- 大量配信のスループットが出ない。

**本番運用前に BullMQ + Redis への移行が必要。**

## 移行方針

`dispatchPendingNotifications()` の呼び出し元を差し替えるだけでよい。
Outbox のスキーマ・claim ロジック・バックオフはそのまま使える。
