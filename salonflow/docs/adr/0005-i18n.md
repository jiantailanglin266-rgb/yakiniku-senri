# ADR-0005: next-intl ではなく軽量な自前 i18n を使う

- 状態: 採用
- 日付: 2026-08-03

## 背景

仕様書 §3 は next-intl を、§16 は以下のファイル構成を要求している。

```
messages/admin/ja.json
messages/admin/en.json
messages/booking/ja.json
messages/booking/en.json
```

## 決定

要求されたファイル構成をそのまま採用し、
`src/i18n/index.ts` に薄い辞書ローダーを実装する（約 100 行）。

```ts
const t = getTranslator("admin", "ja");
t("nav.dashboard");
t("appointment.noShowWarning", { count: 3 });
```

## 理由

- Phase 1 が i18n に求めるのは、名前空間分離・ドット記法・変数埋め込み・
  フォールバックの 4 つだけ。next-intl の機能の大半（複数形規則、
  リッチテキスト、ルーティング統合）は使わない。
- next-intl は Next.js のルーティングとミドルウェアに深く統合される。
  Next.js 16 で `middleware` が `proxy` に改称された直後であり、
  互換性リスクを負いたくなかった。
- API 形状を next-intl に寄せてあるため、移行時の変更は
  `getTranslator` の実装のみで済む。

## 実装上の判断

- **未知のキーはキー自体を表示する。** 空白を返すと不具合が見えなくなる。
  画面に `booking.step.confirm` と出ていれば、それは即座にバグ報告になる。
- 既定ロケールへのフォールバックを 1 段だけ行う。
- 通知テンプレートは DB（`MessageTemplate`）側で多言語化する。
  店舗ごとに文面を変えられる必要があるため、静的ファイルでは足りない。

## 帰結

### 良い点

- 依存ゼロ、RSC でそのまま動く。
- 仕様書が要求するファイル構成に完全準拠。

### 悪い点

- 複数形規則がない（日本語では不要だが、英語で数量表現を書くとき手当てが要る）。
- 日付・数値の書式は `Intl` を直接呼ぶ必要がある。
- 簡体字・繁体字・韓国語の辞書は未作成（型としては定義済み）。
