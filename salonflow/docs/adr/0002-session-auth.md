# ADR-0002: Auth.js ではなく自前の DB セッション認証を使う

- 状態: 採用
- 日付: 2026-08-03

## 背景

仕様書 §3 は認証に Auth.js または Clerk を推奨している。
一方 §10 のデータモデルには `UserSession`（ipAddress / userAgent / deviceLabel /
revokedAt / revokedReason を持つ）が含まれており、DB セッションが前提になっている。

## 決定

`src/server/auth` に**自前のサーバーサイド DB セッション認証**を実装する。
パスワードは Node 標準の scrypt でハッシュする。

## 理由

- 仕様書自身のデータモデルが DB セッションを要求している。Auth.js の JWT 戦略とは合わず、
  database 戦略を使っても `UserSession` の要求カラムはカスタムアダプタが必要になる。
- 仕様書 §8 が要求する「デバイス管理」「セッション失効」「不審ログイン検知」は、
  セッション行を自分で持っていないと実装できない。
- 認証はテナント解決と不可分（どの法人として振る舞うか）であり、
  外部ライブラリのセッションに独自フィールドを載せる構成は結局自前実装に近づく。
- Next.js 16 は 2026 年時点で新しく、認証ライブラリの互換性リスクを
  最重要経路に持ち込みたくない。

## scrypt を選んだ理由

argon2 のほうが望ましいが、ネイティブビルドを伴う。
デプロイ時のビルド失敗が認証停止に直結する。scrypt は Node 標準でメモリハードであり、
OWASP の推奨パラメータ（N=2^16, r=8, p=1）を満たす。

## 帰結

### 良い点

- `UserSession` の要求項目をそのまま実装できる。
- セッション失効・デバイス一覧・強制ログアウトが素直に書ける。
- 依存が 1 つ減る。

### 悪い点

- OAuth / パスキー / MFA を自分で実装する必要がある（Phase 2）。
- 認証コードの正しさが自分たちの責任になる。
  → パスワード検証、トークンハッシュ、定数時間比較を結合テストで検証している。

## 移行方針

`src/server/auth/session.ts` と `context.ts` が唯一の認証境界である。
Auth.js へ移行する場合、`resolveSession()` の実装を差し替えれば
アプリケーション層は変更不要。
