# ADR-0001: 単一 Next.js アプリで開始し、境界だけ先に敷く

- 状態: 採用
- 日付: 2026-08-03

## 背景

仕様書 §23 は `apps/{admin,booking,api}` + `packages/*` の Turborepo 構成を推奨している。
一方 §23 末尾は「小規模 MVP として開始する場合は単一 Next.js アプリでも構いませんが、
将来分割しやすい境界を保ってください」とも述べている。

## 決定

Phase 1 は**単一 Next.js アプリ**で構築する。ただし、仕様書の package 構成に
1:1 対応するディレクトリ境界を最初から敷き、依存方向を一方向に保つ。

## 理由

- 管理画面と予約画面は、メニュー・スタッフ・空き枠計算という同じドメインモデルを共有する。
  分割すると Phase 1 の開発時間の大半が package 間の型共有とビルド設定に消える。
- Turborepo は 3 つのアプリが**別々にデプロイされる**とき価値を持つ。
  Phase 1 は 1 プロセスで動く。
- 境界は物理的な package 分割ではなく、**依存方向の規律**で担保できる。
  `app → modules → domain/infra` の一方向を守っていれば、分割は機械的な作業になる。

## 帰結

### 良い点

- ドメイン層（`booking-engine`, `lib/*`）が I/O 非依存の純関数のままなので、
  切り出しは `package.json` を足すだけになる。
- 単体テストが DB もサーバーも必要とせず、0.1 秒で回る。

### 悪い点

- 規律がコードレビューに依存する。ビルドが逆流を止めてくれない。
- 管理画面と予約画面を別々にスケールできない。

### 分割が必要になる兆候

- 予約画面のトラフィックが管理画面と数桁違い、独立したスケーリングが要るとき
- 管理画面と予約画面のリリースサイクルを分けたいとき
- ビルド時間が開発の妨げになるとき
