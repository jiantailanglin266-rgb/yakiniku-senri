# セキュリティ設計

OWASP ASVS を参照しつつ、サロン管理 SaaS に固有のリスクへ対処した設計をまとめます。

- 最終更新: 2026-08-03
- 対象: SalonFlow Phase 1

---

## 1. 脅威モデル（このシステム固有）

一般的な Web アプリのリスクに加え、本システムには以下の固有リスクがあります。

| # | 脅威 | 影響 | 対策 |
| --- | --- | --- | --- |
| T-1 | **テナント越境** — A 社のスタッフが B 社の顧客・カルテを見る | 致命的 | §3 |
| T-2 | **カルテ写真の流出** — 身体・肌・爪・髪の画像 | 致命的 | §6 |
| T-3 | **顧客リストの一括持ち出し** — CSV での大量エクスポート | 致命的 | §5 |
| T-4 | **重複予約** — 同じ枠に 2 人 | 高（業務停止） | §7 |
| T-5 | **権限昇格** — スタッフが店長機能を実行 | 高 | §4 |
| T-6 | **IDOR** — 他人の予約 ID を推測してアクセス | 高 | §3, §6 |
| T-7 | **公開予約 API の悪用** — 空き枠の総当たり、大量の偽予約 | 中 | §8 |
| T-8 | **CSV インジェクション** — 顧客名に数式を仕込み、CSV を開いた店舗で実行 | 中 | §9 |

## 2. 認証

### 2-1. 方式

自前のサーバーサイド DB セッション認証（[ADR-0002](../adr/0002-session-auth.md)）。

| 項目 | 実装 |
| --- | --- |
| パスワードハッシュ | scrypt（N=2^16, r=8, p=1, 32 バイト鍵、16 バイトソルト） |
| 保存形式 | `scrypt$N$r$p$saltHex$hashHex` |
| 正規化 | 入力を NFKC 正規化してからハッシュ（合成/分解の差異を吸収） |
| 比較 | `timingSafeEqual` による定数時間比較 |
| セッショントークン | 32 バイト CSPRNG、base64url |
| DB 保存 | **SHA-256 ハッシュのみ**。生トークンは Cookie にしか存在しない |
| Cookie | `HttpOnly`, `SameSite=Lax`, `Secure`（本番）, `Path=/` |

セッショントークンに遅い KDF ではなく SHA-256 を使うのは、
トークンが 256 ビットの CSPRNG 出力であり、保護すべき低エントロピーの秘密が
存在しないためです。

### 2-2. セッション失効

| 条件 | 挙動 |
| --- | --- |
| 絶対期限 | 既定 12 時間（`SESSION_TTL_SECONDS`） |
| アイドル期限 | 既定 7 日（`SESSION_IDLE_DAYS`）。超過時に自動失効 |
| 明示的ログアウト | `revokedAt` を記録し監査ログへ |
| ユーザー削除 | 解決時に拒否 |

`lastSeenAt` の更新は 1 分に 1 回へ throttle しています。
更新しなければアイドルタイムアウトが機能せず、毎回更新すれば
読み取り中心のダッシュボードが書き込み中心になるためです。

### 2-3. Brute-force 対策

| 対策 | 既定値 |
| --- | --- |
| 失敗回数によるロック | 5 回 → 15 分ロック（`AUTH_MAX_FAILED_ATTEMPTS` / `AUTH_LOCK_MINUTES`） |
| IP 単位のレート制限 | 10 リクエスト / 分（`RATE_LIMIT_AUTH_PER_MINUTE`） |
| ユーザー列挙対策 | 存在しないアドレスでもダミーハッシュを計算し、応答時間差を作らない |
| エラーメッセージ | 「メールアドレスまたはパスワードが正しくありません」に統一 |

ロック状態のみ専用メッセージを返します。正当な利用者に理由を伝える価値が、
すでに複数回失敗したアドレスについて漏れる情報量を上回ると判断しました。

### 2-4. 未実装（Phase 2）

- MFA（TOTP）
- パスキー（WebAuthn）
- OAuth（Google / Microsoft）
- SSO / SAML
- 不審ログイン検知
- パスワードリセットフロー

**Phase 1 の認証強度はパスワードのみに依存します（リスク R-08）。**
本番投入前に MFA の実装が必須です。

## 3. テナント分離

システムで最も重要な境界です。

### 3-1. 三段階の検証

すべての重要操作で以下を順に検証します。

1. **認証** — 有効な `UserSession` が存在するか
2. **テナントスコープ** — 対象の `organizationId` がセッションの法人と一致するか
3. **権限 + 店舗スコープ** — 必要な Permission を保持し、対象 `storeId` がアクセス可能か

### 3-2. クライアント入力を信用しない

リクエストボディやクエリに含まれる `organizationId` / `storeId` は
**一切信用しません**。セッションから導出した値のみを Repository へ渡します。

クライアントから受け取った `storeId` は「これにアクセスしたい」という
希望としてのみ扱い、`requireStoreAccess()` で検証してから使用します。

### 3-3. 実装

`src/server/db/tenant.ts` が唯一のスコープ生成点です。

```ts
orgScope(context)        // { organizationId, deletedAt: null }
storeScope(context, id?) // 店舗アクセス権を検証したうえで絞り込む
assertTenant(context, row)      // 主キー取得後の所属検証
assertTenantStore(context, row) // 加えて店舗の可視性も検証
```

`findUnique({ where: { id } })` はテナント条件を持てないため、
取得後に `assertTenant()` で検証するのが規約です。

### 3-4. 情報漏えいを避けるエラー

存在しない ID と、他テナントの ID は**同一のエラーメッセージ**を返します。
「存在するがあなたのものではない」という区別自体が情報漏えいだからです。
この不変条件は結合テストで検証しています。

### 3-5. 検証

`tests/integration/tenant-isolation.test.ts` で以下を検証しています。

- 顧客一覧に他テナントの顧客が含まれない
- 他テナントの顧客 ID を指定しても `null` が返る
- 他テナントの顧客との統合が失敗し、対象レコードが無傷である
- 他テナントの店舗を指定した台帳取得が `AuthorizationError` になる
- 他テナントのカルテが読めない（自テナントからは読めることも併せて確認）
- 他テナントのカルテテンプレートを使ったカルテ作成が失敗する
- 「存在しない」と「他人のもの」のエラーメッセージが一致する

## 4. 認可（RBAC + 店舗スコープ）

詳細は [PERMISSIONS.md](../PERMISSIONS.md) を参照してください。

### 4-1. 構造

```
User ──< UserRole >── Role ──< RolePermission >── Permission
              │
              └── storeId（null = 法人全店）
```

権限は「グローバル（法人全体）」と「特定店舗のみ」の 2 種類に分かれます。
`can(context, permission, storeId)` は両方を確認します。

### 4-2. 項目単位マスキング

権限とは別軸で、ロールに表示制限フラグを持たせます。

| フラグ | 挙動 |
| --- | --- |
| `maskCustomerPhone` | 下 2 桁のみ表示 |
| `maskCustomerEmail` | ローカル部を伏せ字 |
| `maskSalesAmount` | 金額を `null` にして返す |
| `maskMedicalPhoto` | 署名付き URL を発行しない |
| `maskStaffCompensation` | 歩合・目標を `null` にして返す |

**マスキングはサーバー側で値を落としてから返します。**
CSS で隠すだけでは、閲覧権限のないブラウザへ値そのものが送られてしまいます。

マスキングは CSV 出力にも適用されます。画面で見られない値をファイルで
取得できてしまっては意味がないためです。

### 4-3. 運営者はカルテを見られない

`platform_admin` ロールは意図的に `medical_record.read` / `medical_record.write` を
持ちません。SaaS 提供者がサロン顧客の身体情報へ無制限にアクセスできる設計は、
委託先管理の観点から避けるべきと判断しました。
緊急時の手続きは [OPERATIONS.md](../operations/OPERATIONS.md) に別途規定します。

| CSV インジェクション対策 | §9 |

## 6. カルテ写真の保護

| 対策 | 実装 |
| --- | --- |
| 直接 URL の禁止 | `storageKey` のみ DB に保持。公開パスは存在しない |
| 署名付き URL | HMAC-SHA256（`SESSION_SECRET` 由来）、既定 300 秒で失効 |
| **二重チェック** | 署名の検証に加え、配信時にセッションと権限を再確認 |
| パストラバーサル対策 | キーの文字種制限 + 解決後パスがルート配下であることの確認 |
| キャッシュ制御 | `private, no-store` |
| 監査ログ | カルテ閲覧・写真表示を記録 |

署名付き URL が転送されても、受け取った相手にセッションと権限がなければ
配信されません。**URL だけでは不十分**という設計です。

## 7. 重複予約防止

詳細は [PHASE0_DESIGN.md §7](../PHASE0_DESIGN.md) を参照してください。

```sql
EXCLUDE USING gist (
  "staffId" WITH =,
  tstzrange("startAt", "endAt", '[)') WITH &&
) WHERE ("isActive")
```

アプリ側の `SELECT ... WHERE overlaps` だけでは、
2 つのトランザクションが互いの未コミット行を見られないため競合を検出できません。
**排他制約が唯一の確実な手段**です。

多層防御：

1. 表示時の空き枠計算（非拘束）
2. 冪等キーによる二重送信防止
3. 確定直前のトランザクション内再検証
4. **DB 排他制約**（最終防波堤）
5. 直列化失敗時の 1 回リトライ

同時 5 リクエストで 1 件だけが成立することを結合テストで検証しています。

## 8. Web 一般の対策

### 8-1. HTTP ヘッダ

`next.config.ts` で全レスポンスに付与しています。

| ヘッダ | 値 |
| --- | --- |
| `Content-Security-Policy` | `default-src 'self'` ほか。`frame-ancestors 'none'`, `object-src 'none'` |
| `Strict-Transport-Security` | `max-age=63072000; includeSubDomains; preload` |
| `X-Content-Type-Options` | `nosniff` |
| `X-Frame-Options` | `DENY` |
| `Referrer-Policy` | `strict-origin-when-cross-origin` |
| `Permissions-Policy` | `camera=(), microphone=(), geolocation=(), payment=(), usb=()` |

> **既知の弱点**: CSP に `'unsafe-inline'` が含まれます。
> Next.js のインラインブートストラップと Tailwind のインラインスタイルのためです。
> 本番投入前に nonce 方式へ移行してください。

### 8-2. CSRF

`src/proxy.ts`（Next.js 16 で `middleware` から改称）が、
状態変更メソッド（POST / PUT / PATCH / DELETE）について `Origin` を検証します。
Server Actions と JSON API はどちらも Cookie に依存するため、
自サイト以外の `Origin` は CSRF とみなして 403 を返します。

Cookie の `SameSite=Lax` も併用しています（`Strict` にしないのは、
予約確認メールのリンクから来た顧客がログアウト状態の画面に着地しないため）。

**認証は proxy では行いません。** proxy はルート解決前に動作しテナントを知り得ないため、
各ページ・ハンドラが自らセッションを解決します。
「proxy が通したから検証済みのはず」という隙間を作らないためです。

### 8-3. XSS

- React による自動エスケープ
- `dangerouslySetInnerHTML` を使用していない
- 通知テンプレートの置換は `[a-zA-Z0-9_]` のトークンのみ。式評価は一切しない
- 未知のトークンは `undefined` に置換せず、そのまま残す（typo が可視化される）

### 8-4. SQL インジェクション

Prisma のパラメータ化クエリのみを使用し、生 SQL は使用していません
（マイグレーション内の DDL を除く）。

### 8-5. レート制限

| スコープ | 既定値 |
| --- | --- |
| ログイン | 10 / 分 / IP |
| 公開空き枠 API | 60 / 分 / IP |
| 公開予約作成 | 10 / 分 / IP |

> **既知の制約**: Phase 1 の実装はプロセスメモリ内の固定ウィンドウです。
> 複数インスタンス構成ではインスタンスごとに独立した予算になります。
> 本番では Redis への移行が必要です（リスク R-16）。

### 8-6. 冪等性

公開予約 API は `Idempotency-Key` ヘッダを受け付け、`IdempotencyRecord` に記録します。

| 状況 | 応答 |
| --- | --- |
| 同一キー・同一内容・完了済み | 保存済みレスポンスを再生 |
| 同一キー・**異なる内容** | `409 IDEMPOTENCY_KEY_REUSED` |
| 同一キー・処理中 | `409 REQUEST_IN_FLIGHT` |

失敗時はキーを解放します。顧客が別の枠を選んですぐ再試行できるようにするためです。

### 8-7. SSRF

Phase 1 では外部への HTTP リクエストを行いません。
Webhook 配信（Phase 3）を実装する際は、送信先 URL の検証
（プライベート IP・メタデータエンドポイントの拒否）が必須です。

## 9. CSV インジェクション

顧客名や備考に `=cmd|'/c calc'!A1` のような値が入っていると、
CSV を Excel で開いた店舗側で数式として実行されます。

`escapeCsvCell()` が、先頭が `=` `+` `-` `@` タブ CR のセルに
シングルクォートを前置します。加えて区切り文字・引用符・改行を含むセルを
引用符で囲みます。

単体テストで実際の攻撃文字列を用いて検証しています。

## 10. 監査ログ

### 10-1. 記録対象

ログイン成否、アカウントロック、ログアウト、予約の作成・変更・状態遷移、
顧客の閲覧・作成・更新・統合・削除・CSV 出力、
カルテの閲覧・写真表示・作成・更新、売上変更・返金、権限変更、設定変更、
API キー作成、データインポート。

### 10-2. 記録項目

`actorId`, `organizationId`, `storeId`, `action`, `entityType`, `entityId`,
`before`, `after`, `ipAddress`, `userAgent`, `requestId`, `createdAt`

### 10-3. 記録しない情報

以下のフィールド名は値を `[redacted]` に置換します（ネストも再帰的に処理）。

```
password, passwordHash, newPassword, currentPassword, secret, previousSecret,
token, tokenHash, keyHash, accessToken, refreshToken, apiKey, authorization,
cookie, cardNumber, pan, cvv, cvc, securityCode, providerToken, signatureData
```

長すぎる文字列は 2,000 文字で切り詰めます。

### 10-4. 書き込み失敗の扱い

監査ログの書き込み失敗は、それが記述する業務操作をロールバックさせません
（呼び出し側が `tx` を渡した場合を除く）。
失敗自体はアプリケーションログへ `error` レベルで出力されます。

## 11. 決済カード情報

**自社 DB にカード情報を保存しません。** 決済事業者のトークンのみを
`Payment.providerToken` に保持する設計です。
Phase 1 では決済を実装していません。

## 12. 既知の弱点（Phase 1）

正直に記載します。本番投入前に対処が必要です。

| # | 弱点 | 影響 | 対処 |
| --- | --- | --- | --- |
| W-1 | MFA / パスキー未実装 | 認証強度がパスワードのみに依存 | Phase 2 |
| W-2 | CSP に `'unsafe-inline'` | XSS 時の被害拡大余地 | nonce 方式へ移行 |
| W-3 | レート制限がプロセスメモリ内 | 複数インスタンスで実効値が緩む | Redis 化 |
| W-4 | 保存データの暗号化なし | DB / ストレージ流出時に平文 | 列暗号化 or 透過暗号化 |
| W-5 | データ保持期間の自動削除なし | 不要データの滞留 | 保持期間ジョブの実装 |
| W-6 | 監査ログの改ざん防止なし | 内部犯行の追跡性 | 追記専用ストア or 署名 |
| W-7 | パスワードリセット未実装 | 運用で手動対応が必要 | Phase 2 |
| W-8 | ジョブがインプロセス | 複数インスタンスで重複送信の可能性 | BullMQ 化 |
| W-9 | 外部セキュリティテスト未実施 | 未知の脆弱性 | 公開前に実施 |
