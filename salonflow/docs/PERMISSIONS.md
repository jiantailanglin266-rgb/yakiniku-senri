### 運営者がカルテを見られない理由

SaaS 提供者がサロン顧客の身体情報（肌・爪・髪の状態、施術写真）へ
無制限にアクセスできる設計は、委託先管理の観点から避けるべきと判断しました。

障害調査で必要になった場合は、[OPERATIONS.md](operations/OPERATIONS.md) の
緊急アクセス手続き（テナントの明示的同意 + 期限付き付与 + 監査記録）に従います。

## 3. 項目単位マスキング

権限とは独立した表示制限です。ロールごとに設定します。

| ロール | 電話 | メール | 売上 | カルテ写真 | 給与 | 自分の担当のみ |
| --- | :-: | :-: | :-: | :-: | :-: | :-: |
| 運営者 | 表示 | 表示 | 表示 | **非表示** | 非表示 | − |
| 法人オーナー | 表示 | 表示 | 表示 | 表示 | 表示 | − |
| 店舗オーナー | 表示 | 表示 | 表示 | 表示 | 表示 | − |
| 店長 | 表示 | 表示 | 表示 | 表示 | 非表示 | − |
| 受付 | 表示 | 表示 | 表示 | **非表示** | 非表示 | − |
| スタッフ | **マスク** | **マスク** | 表示 | 表示 | 非表示 | **○** |
| 業務委託 | **マスク** | **マスク** | 表示 | 表示 | 非表示 | **○** |
| 経理 | マスク | マスク | 表示 | 非表示 | 表示 | − |
| マーケ | マスク | マスク | **非表示** | 非表示 | 非表示 | − |
| 閲覧専用 | マスク | マスク | **非表示** | 非表示 | 非表示 | − |

### マスキングの実装

- **サーバー側で値を落としてから返します。** CSS で隠すだけでは、
  権限のないブラウザへ値そのものが送られてしまいます。
- CSV 出力にも同じマスクが適用されます。
- 電話番号は下 2 桁のみ（`*********78`）、
  メールはローカル部を伏せ字（`h*****@example.com`）にします。
- 金額は `null` にして返し、UI が「権限がないため非表示」を描画します。

### 複数ロールを持つ場合

マスクは**論理積**で解決します。値を見られるロールを 1 つでも持っていれば表示されます。
`restrictToOwnRecords` も同様に、制限のないロールがあれば制限が外れます。

## 4. 店舗スコープ

`UserRole.storeId` が `null` なら法人全店、値があればその店舗のみに適用されます。

```
can(context, permission, storeId)
  = globalPermissions.has(permission)
  || storePermissions.get(storeId)?.has(permission)
```

`storeId` を省略した `can()` は「どこかの店舗で持っているか」を返します。
これはナビゲーション項目の表示可否の判断にのみ使用し、
実際の操作では必ず `storeId` を指定します。

### 店舗アクセスの検証

```ts
requireStoreAccess(context, storeId)  // アクセス可能店舗集合に含まれるか
scopedStoreIds(context, storeId?)     // クエリを絞り込む店舗 ID 集合
```

台帳取得などでは、テナントフィルタで空が返ることに頼らず、
**明示的に `requireStoreAccess()` で拒否**します。
「見られない店舗を指定したら空の台帳が返る」のではなく、
「アクセス権がない」と応答するのが正しい挙動だからです。

## 5. 「自分の担当のみ」制限

`restrictToOwnRecords` が true のロール（スタッフ・業務委託）は：

| 画面 | 挙動 |
| --- | --- |
| 予約台帳 | 自分の列のみ表示 |
| 予約一覧 | 自分が担当する予約のみ |
| 顧客一覧 | 自分が施術したことのある顧客のみ |
| カルテ一覧 | 自分が作成したカルテのみ |

`Staff.userId` によるログインアカウントとの紐付けが前提です。
紐付けのないユーザーには制限が適用できないため、
そもそもこれらのロールを付与すべきではありません。

---

## 6. 認可の実装規約

1. **すべての重要操作はサーバー側で認可する。** UI でボタンを隠すのは利便性であり、制御ではない。
2. **モジュール層の関数は `RequestContext` を引数に取る。** グローバルなセッション参照は行わない。
3. **クライアントから来た `organizationId` / `storeId` は信用しない。** セッションから導出した値のみを使う。
4. **`findUnique` で主キー取得した行は `assertTenant()` で検証する。**
5. **存在しない ID と他テナントの ID は同一のエラーを返す。**

## 7. 検証

権限設計は以下でテストされています。

- `tests/unit/permissions.test.ts` — カタログの整合性、ロール定義の不変条件
- `tests/integration/tenant-isolation.test.ts` — 実際の越境試行と拒否

特に検証している不変条件：

- 定義済み権限がすべてカタログに文書化されている
- ロールが存在しない権限を参照していない
- 法人オーナーが全権限を持つ
- 運営者がカルテ権限を持たない
- 閲覧専用が書き込み権限を持たない
- `customer.export` が上位 3 ロールに限定されている
- スタッフ・業務委託が `restrictToOwnRecords` である
